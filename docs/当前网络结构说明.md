# 当前网络结构说明

本文档基于当前代码分支的默认配置来讲，也就是：

- `cfg/algo/mappo.yaml`
- `omni_drones/learning/mappo.py`
- `omni_drones/learning/common.py`
- `omni_drones/learning/modules/networks.py`
- `omni_drones/learning/modules/distributions.py`
- `omni_drones/utils/torchrl/transforms.py`
- `omni_drones/envs/hide_and_seek/hideandseek.py`

我会尽量用大白话来讲，避免只堆代码名词。

## 1. 一句话先讲清楚

现在这套网络，不是一个“大一统黑箱”。

它其实可以拆成 3 个部分：

1. `TP 预测网络`
   负责先猜目标未来几步会往哪跑。
2. `Actor`
   负责给每架追捕无人机输出动作。
3. `Critic`
   负责在 RL 训练时评估“当前局面值不值、好不好”。

大流程就是：

```text
历史信息 -> TP 预测目标未来位置
当前观测 + 预测结果 -> Actor 输出 4 维动作
4 维动作 -> PIDRateController -> 真实控制命令
```

## 1.5 数据流到底怎么走

如果只看“无人机每一步是怎么动起来的”，当前这套网络的数据流可以画成下面这样。

### 1.5.1 推理 / 执行时的数据流

```text
目标历史轨迹
    -> TP 网络（LSTM）
    -> 未来 5 步目标位置预测

环境当前观测
    -> state_self
    -> state_others
    -> cooperation

TP 预测结果 + 当前观测
    -> Actor 编码器（CoopEntityAttentionEncoder）
    -> actor feature（128维）
    -> 动作分布头（TanhIndependentNormalModule）
    -> 4维动作
       [omega_x, omega_y, omega_z, thrust]
    -> PIDRateController
    -> 底层控制命令
    -> Isaac Sim / 物理仿真
    -> 下一时刻状态
```

大白话说：

- `TP` 先负责“看趋势”
- `Actor` 再负责“现在该怎么打舵、给多大推力”
- `PIDRateController` 负责把网络动作翻译成真正能执行的控制命令
- 最后仿真器把这个动作变成下一时刻的真实运动结果

### 1.5.2 训练时的数据流

如果看训练过程，数据流会多出 `Critic` 和损失函数这一条线：

```text
环境 rollout
    -> observation / state / reward / done

observation
    -> Actor
    -> 动作
    -> 环境继续 rollout

state
    -> Critic
    -> value

reward + value + rollout
    -> PPO / BC / DAgger 损失
    -> 反向传播
    -> 更新 Actor / Critic（TP 视具体阶段而定）
```

也就是说：

- `Actor` 负责出动作
- `Critic` 负责告诉训练器“这个局面大概值不值”
- `TP` 是额外的目标运动预测模块
- 三者一起组成了整个训练闭环

## 2. 当前任务里，网络到底看到了什么

当前 `HideAndSeek` 任务里，追捕方的观测主要分成 3 块：

1. `state_self`
   表示“我自己现在的状态”
2. `state_others`
   表示“另外两架队友的状态”
3. `cooperation`
   表示一些协作相关的额外信息

按当前任务配置，维度大概是这样：

- `state_self`: `32`
- `state_others`: `2 x 8`
- `cooperation`: `1 x 10`

为什么 `state_self = 32`？

因为它大概是这些信息拼起来的：

- 当前目标相对信息 `3`
- TP 预测的未来目标位置 `3 x future_predcition_step = 15`
- 时间编码 `1`
- 自身飞行相关状态 `13`

合起来就是：

```text
3 + 15 + 1 + 13 = 32
```

而当前配置里：

- `future_predcition_step = 5`
- `history_step = 10`
- `window_step = 1`

所以 TP 网络每次会预测目标未来 `5` 步的位置。

## 3. 一个很重要的误区

很多人看到 `mappo.yaml` 里有这些配置，会以为当前主干网络是“MLP 256-256-256 + MobileNet”：

- `hidden_units: [256, 256, 256]`
- `vision_encoder: MobileNetV3Small`

但**对当前这个任务来说，不是这样**。

原因很简单：

- 当前观测没有图像输入
- 当前观测是 `CompositeSpec`
- 所以代码会走“实体编码器 / 注意力编码器”这条路

也就是说：

**当前真正工作的主干，不是 MobileNet，也不是那组普通 MLP。**

现在真正工作的，是：

- Actor: `CoopEntityAttentionEncoder`
- Critic: `RelationEncoder`

这点非常重要。

## 4. Actor 现在到底长什么样

### 4.1 Actor 的核心思路

Actor 不是把所有东西一股脑摊平后塞进一个大 MLP。

它更像是在做：

1. 先把“自己”和“队友”编码成一组 token
2. 再让“自己”去关注队友
3. 最后根据这个合作后的特征，输出动作

所以它本质上是一个：

**“自机为中心的协作注意力网络”**

### 4.2 当前默认的 Actor 编码器

当前默认 Actor 编码器是：

- `CoopEntityAttentionEncoder`

它的做法是：

1. 把 `state_self + cooperation` 拼起来，做成一个“自机 token”
2. 把 `state_others` 变成“队友 token”
3. 然后用一个小型 Transformer，让自机 token 去关注这些队友 token
4. 最后取编码后的自机 token，作为 Actor 的特征表示

当前默认结构大概是：

- token 维度：`128`
- attention 头数：`4`
- Transformer 层数：`2`
- 前馈层宽度：`256`

最后输出一个：

- `128` 维 actor feature

### 4.3 当前 Actor 是不是 GRU

**默认不是。**

虽然代码里保留了 `GRU` 支持，但在当前默认配置里：

- `actor.rnn` 是注释掉的

所以按“当前默认结构”来说：

- Actor 没开 GRU
- Actor 主要靠当前时刻观测和 TP 预测来出动作

如果你以后重新打开 `rnn` 配置，那才会进入 recurrent actor 模式。

### 4.4 当前 Actor 输出什么

当前 Actor 最后输出的是每架无人机的 `4` 维动作：

```text
[omega_x, omega_y, omega_z, thrust]
```

更准确地说，是一个**归一化后的 4 维控制动作**。

现在因为你把：

- `algo.actor.tanh = true`

打开了，所以 Actor 现在用的是：

- `TanhIndependentNormalModule`

也就是：

- 先输出一个高斯分布
- 再通过 `tanh` 把动作压到 `(-1, 1)`

这样做的好处是：

- 动作天然有界
- 不会像以前那样 raw action 一路飙到几十

### 4.5 当前 Actor 的分布头

Actor 的动作头现在大概是这样：

1. 编码器输出 `128` 维特征
2. 一个线性层 `fc_mean: 128 -> 4`
3. 再配一个全局可学习的 `log_std`

当前 `log_std` 配置是：

- `log_std_init = -3.0`
- `log_std_min = -5.0`
- `log_std_max = -1.0`

大白话说：

- 均值由当前状态决定
- 方差有一个全局可学参数
- 但你现在把它压得比较低，目的是别让 warm-start 一上来探索太疯

### 4.6 三架无人机是不是各用一套 actor

**不是。**

当前配置里：

- `share_actor = true`

这表示：

**三架追捕无人机共用同一套 actor 权重。**

也就是说：

- 不是 3 个完全独立的策略网络
- 而是 1 套共享策略，分别喂给 3 架机自己的观测

这样做的好处是：

- 参数更省
- 更容易泛化
- 也更符合“同类无人机用同一策略”的直觉

## 5. Critic 现在到底长什么样

### 5.1 Critic 的角色

Critic 不负责出动作。

它的任务是：

- 看当前局面
- 估计“这个局面值多少钱”

在 PPO 训练里，Critic 主要是帮助 Actor 判断：

- 刚才这步动作到底是好是坏

### 5.2 当前默认 Critic 的输入

当前配置里：

- `critic_input = state`

这意味着 Critic 看的不是每架机自己的局部 observation，
而是一个更集中式的全局 state。

当前 `state_drones` 的维度大概是：

- `3 x 42`

为什么是 `42`？

因为每架机的全局 state token 里大概包含：

- 目标相关信息 `3`
- TP 未来预测 `15`
- 时间编码 `1`
- 飞行状态 `13`
- 协作信息 `10`

合起来：

```text
3 + 15 + 1 + 13 + 10 = 42
```

### 5.3 当前默认 Critic 编码器

当前默认 Critic 编码器是：

- `RelationEncoder`

它的思路和 Actor 不太一样。

Actor 更像是：

- “我自己看队友”

Critic 更像是：

- “把所有无人机之间的两两关系都看一遍”

它大致在做：

1. 先把每架无人机编码成一个 token
2. 构造所有 token 两两之间的组合
3. 让网络学习“这对关系意味着什么”
4. 再把这些关系聚合起来
5. 输出一个全局价值特征

最后 Critic 也会得到一个：

- `128` 维的全局特征

然后接一个 value head 输出状态价值。

### 5.4 当前默认 Critic 是不是 RNN

默认也**不是**。

和 Actor 一样：

- `critic.rnn` 现在在配置里也是注释掉的

所以当前默认 Critic 是：

- 非循环
- 基于当前时刻状态做估值

## 6. TP 预测网络是什么

TP 网络是这套系统里一个很重要但容易被忽略的部分。

它不是直接负责控制无人机，
而是负责：

**先猜目标未来几步会跑到哪里。**

### 6.1 TP 网络的结构

当前 TP 网络是一个很简单直接的：

- `1` 层 `LSTM`
- hidden size `64`
- 后接一个 `Linear`
- 最后再 `tanh`

也就是：

```text
历史序列 -> LSTM(64) -> Linear -> 未来目标位置
```

### 6.2 TP 的输入输出

当前 TP 输入大概是：

- `history_step = 10`
- 每步输入维度 `19`

也就是：

```text
[10, 19]
```

这个 `19` 主要来自：

```text
1 + 3 + 3 + max_agents * 3
```

其中：

- `1`：一些标记量
- `3`：目标位置或相关量
- `3`：目标速度或相关量
- `max_agents * 3 = 4 * 3 = 12`：最多 4 个智能体的位置相关信息

所以：

```text
1 + 3 + 3 + 12 = 19
```

TP 输出是：

- `3 * future_predcition_step = 15`

也就是未来 `5` 步、每步 `3` 维位置。

再 reshape 后就是：

```text
[5, 3]
```

### 6.3 TP 和 Actor 的关系

TP 不是替代 Actor，
而是给 Actor 提供一个更“提前量”的目标信息。

你可以理解成：

- Actor 负责“怎么追”
- TP 负责“先告诉你目标可能往哪跑”

所以现在 Actor 看到的 `state_self` 里，已经包含了 TP 的预测结果。

## 7. 动作输出后，怎么真正进仿真

这是很关键的一层。

现在 Actor 输出的 4 维动作，不会直接变成电机转速。

它中间还要经过：

- `PIDRateController`

当前流程是：

1. Actor 输出 `4` 维归一化动作
2. 因为现在 `actor.tanh=true`，动作已经在 `(-1, 1)`
3. `PIDRateController` 不再额外做一次 `torch.tanh`
4. 前 `3` 维当作目标角速度比例
5. 最后 `1` 维当作目标推力比例
6. 再映射到真实控制量，交给底层控制器生成命令

大白话就是：

- Actor 不是直接控电机
- Actor 是在输出“想要多大角速度、想要多大推力”
- 然后底层控制器再把它翻译成真正能执行的命令

### 9.1 全流程模块核心解析

根据这幅详尽的数据流图，我们可以清晰地看到每一个张量（Tensor）是怎么流转并发号施令的：

**1. TP 前端感知处理：**
  目标过去十步飞行的相对信息会被喂入一层带有短时记忆的 `LSTM`，它提炼后交由全连接层将数据变成 **未来 5 步的三维坐标预测 (总计 15 个浮点数)**。这 15 个值会像雷达告警机一样，实时插入到本机的观测底座（`state_self`）里。

**2. Actor 表征提取（CoopEntityAttentionEncoder）：**
  这是当前网络的核心大脑！它兵分两路：第一路把“我自己”的飞行姿态、位置和前面的“雷达告警预测”拼起来，全连接升维成一个 `128 维` 的高维 Token。第二路把“队友的状态”分别升维成数个 `128 维` 的 Token。然后在多头注意力机制（Attention）里，**让“我”作为查询向量去权衡各“队友”，融合出最洞悉周围态势的 `128 维` 战术特征**。

**3. Actor 的分叉（微操执行与战术分析）：**
  在获得了最浓缩的战术特征（128维向量）后，网络劈成了两个不同使命的部分：
  * **主操作手（主特征通路）**：走向了 `TanhIndependentNormal` 动作头。通过线性层塌缩为 4 个独立数值（对应 X/Y/Z 三轴打舵量和主推力均值）。如果正处于 RL 系统，它会引入 `log_std` 进行正态采样试错，并在最后关卡强制采用 `Tanh` 函数锁死至 `(-1, 1)`。
  * **战术参谋部（BC 辅助通路）**：仅在专家数据学习时开机，强拉这 128 维向量“兼职”去做多项填空题（预测敌机航迹、下达防区指派等），利用大 Loss 逼迫 `CoopEntityAttentionEncoder` 不要偷懒，必须构建深度的空间战术直觉。

**4. 控制下发与飞控落地：**
  这 4 维动作信号被剥离出神经网络端，通过接口下发给飞控算法 `PIDRateController`。在这里如同真实世界的串口通讯一样被“映射解压”，转算成无人机能懂的电调 PWM 与旋翼力学驱动量。随即，无人机在 Isaac Sim 的物理迭代中移动，重新开始下一个轮回。

## 10. 从你的方案角度看，网络的创新点在哪里

这一部分我尽量讲得既通俗，又不过分夸大。

如果从“你这个项目方案”的角度来概括，当前网络最值得强调的点主要有下面几条。

### 10.1 端到端输出的是低层控制，而不是高层导航指令

这是你这套方案最核心、也最有辨识度的一点。

很多多无人机任务里，网络输出的往往是：

- 目标速度
- 目标航点
- 或者某种高层期望方向

然后再交给另外一套传统控制器慢慢去跟踪。

但你这里不是这样。

你当前 Actor 直接输出的是：

```text
[omega_x, omega_y, omega_z, thrust]
```

也就是：

- 角速度控制量
- 推力控制量

大白话说：

**你的网络不是在说“往哪飞”，而是在直接说“现在怎么打舵、给多大油门”。**

这点很重要，因为它让策略更接近真正的低层飞行控制，而不是只做一个高层导航器。

### 10.2 在低层控制前，先显式引入目标未来轨迹预测

你这套方案不是只看“目标现在在哪”，而是先用 `TP` 网络预测：

- 目标接下来几步可能往哪跑

然后再把这个预测结果送给 Actor。

这意味着当前 Actor 不是单纯做反应式控制，而是在做一种：

**“带提前量的低层追捕控制”**

大白话说：

- 普通反应式策略更像“看见人在哪，就朝哪追”
- 你这套更像“先猜对方下一步要往哪跑，再提前截他”

这会让你的控制更适合追捕类任务，而不只是一般的点到点飞行。

### 10.3 Actor 不是简单拼平输入，而是显式建模协作关系

你当前 Actor 用的是：

- `CoopEntityAttentionEncoder`

它不是把所有输入直接 flatten 后塞进 MLP，
而是把：

- 自己
- 队友
- 协作信息

拆成更有结构的 token，再通过注意力机制建模。

这意味着你的策略不是单机思维，而是：

**“以自机为中心，但显式考虑队友”的协作控制策略。**

大白话说：

- 不是三架机各飞各的
- 而是每架机都会看“我是谁、队友在哪、我和队友怎么配合”

这点很适合写成“协同感知 / 协同决策”的结构特点。

### 10.4 三架同构追捕者共享一套策略，强调可扩展的同类协作

当前配置里：

- `share_actor = true`

也就是三架追捕无人机共用同一套 Actor 权重。

这背后的意义不是只为了省参数，而是说明你的设计默认假设：

- 三架追捕者是同类体
- 它们应该学会一套共享的协同控制规律

这样做的好处是：

- 参数更少
- 更容易泛化到不同具体个体
- 更符合“多智能体同构协作”的建模思路

如果以后你要写论文，这一点可以和“可扩展性”或者“同构多机协作”联系起来讲。

### 10.5 Critic 采用集中式关系建模，Actor 采用分布式执行

当前这套结构其实还体现了一个很经典但很重要的思想：

- `Actor` 是分布式执行
- `Critic` 是集中式训练

也就是：

- 执行时，每架机只靠自己的 observation 和协作信息来出动作
- 训练时，Critic 会看更完整的全局 state，帮助学习更稳定

再加上 Critic 用的是 `RelationEncoder`，它不是粗暴看全局向量，而是显式看无人机之间的关系。

这点可以概括成：

**“集中式关系估值 + 分布式低层控制”**

对于多无人机协作任务，这是一个很合理、也很容易讲清楚的结构亮点。

### 10.6 一句话怎么概括你的结构特点

如果要压缩成一句比较适合写进介绍里的话，我建议是：

```text
该方法将目标未来轨迹预测、以自机为中心的协作注意力决策、以及端到端低层推力/角速度控制统一到同一套多无人机追捕框架中，并采用集中式关系 Critic 提升训练稳定性。
```

如果再说得大白话一点，就是：

**“先预测目标往哪跑，再让每架机结合队友情况，直接输出低层控制动作去追。”**

## 11. 最后一句话总结

当前默认网络结构可以概括成：

**“一个 LSTM 做目标未来位置预测，一个共享 Actor 用自机中心的协作注意力来输出 4 维推力/角速度动作，一个集中式 Critic 用关系编码器来做全局价值估计。”**

如果再说得更直白一点：

- `TP` 负责“先猜目标往哪跑”
- `Actor` 负责“每架追捕机现在该怎么飞”
- `Critic` 负责“这个局面到底好不好”

而且当前默认结构里：

- 没开 GRU
- 没开辅助头
- 没开上一时刻动作条件分支
- 三架追捕机共用一套 Actor 权重

这就是现在代码里真正生效的主干网络。
