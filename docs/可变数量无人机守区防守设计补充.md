# 可变数量无人机守区防守：Phi_team / D_i / 指标体系 / 奖励函数补充

> 适用范围
>
> - 单目标 `goal-defense` 任务
> - pursuer 数量可变
> - 目标任务是进入守区，我方任务是阻止其进入并在此前完成抓捕
>
> 文档目标
>
> - 给 `multi_uav_cooperation_design.md` 补一版更适合“可变数量 + 守区防守”的协同势函数定义
> - 说明原文档中的差分边际贡献 `D_i` 是否可用
> - 给出一版可行、尽量精简的奖励函数设置
>
> 说明
>
> - 这是一份方案文档，不假设当前代码已经实现
> - 重点是把“协同追捕”与“守区防守”统一到一个可训练的目标里

---

## 1. 先给结论

- `multi_uav_cooperation_design.md` 里的差分边际贡献形式 `D_i = Phi(A) - Phi(A \\ i)` 是对的，可以保留。
- 但其中的 `Phi` 不能只定义成“包围质量”或“角度覆盖质量”，否则更适合纯追捕，不足以表达守区防守。
- 对 `goal-defense` 任务，更合适的 `Phi_team` 应该同时包含：
  - 守区威胁方向上的堵截能力
  - 对 target 的有效压力
  - 在 `N >= 2 / N >= 3` 时才逐步强调展开和包围
- 奖励函数不应重新回到“十几个 shaping 项并列”的状态，而应让：
  - `terminal success/failure`
  - `goal_progress`
  - `capture_progress`
  - `D_i / Phi_team`
  - `cost-based safety`
  成为主干。

---

## 2. 原设计中的差分边际贡献是否可以继续用

原文档中的定义是：

```python
D_i = Phi_team(all agents) - Phi_team(without agent i)
```

这个形式本身没有问题，优点很明确：

- 归因逻辑干净，不依赖人工角色标签
- 对 `N=3` 的场景计算开销很低
- 对可变数量场景天然兼容，只要 `Phi_team` 本身对不同 `N` 有合理定义

但原文档里示例 `Phi_team` 更偏“coverage / encircle”：

- 对纯追捕任务是合理的
- 对“守区防守”任务不够完整

原因是：

- 在守区任务中，最核心的问题不是“围得圆不圆”
- 而是“有没有在 target 通往守区的威胁通道上形成有效堵截”

因此结论是：

- `D_i` 的形式可以直接保留
- 但 `Phi_team` 必须从“包围几何势函数”升级为“守区防守协同势函数”

---

## 3. 设计目标

新的 `Phi_team` 需要同时满足四个要求：

1. 对 `N` 可变时量级稳定，不依赖 `sum`
2. 守区临近时优先强调堵截，而不是继续鼓励漂亮包围
3. `N=1 / 2 / 3+` 时都有合理语义
4. 能直接用于 leave-one-out 归因

核心思路是：

- 用一个团队势函数 `Phi_team` 表示“这一刻整个 pursuer 团队对守区防守到底有多好”
- 再用 `D_i = Phi_team(A) - Phi_team(A \\ i)` 给每架机一个边际贡献信号

---

## 4. Phi_team：守区防守协同势函数

### 4.1 记号

设：

- `A`：当前 active pursuer 集合
- `n = |A|`
- `p_t`：target 当前位置
- `p_g`：守区中心
- `p_pred`：TP 对 target 的未来预测位置
- `u_goal = normalize(p_g - p_t)`：静态守区威胁方向
- `u_tp = normalize(p_pred - p_t)`：预测运动方向

定义威胁方向：

```text
u_th = normalize((1 - beta) * u_goal + beta * u_tp)
```

建议：

- `beta = 0.25`

解释：

- `goal-defense` 任务本质上应以“守区方向”为主
- `TP` 只负责修正 target 的局部规避机动
- 不建议让 `TP` 完全主导 threat direction

### 4.2 守区紧急度门控

令 `d_goal` 为 target 到守区边界的距离，定义：

```text
g_urg = sigmoid((d_crit - d_goal) / tau_urg)
```

建议：

- `d_crit = 0.8m`
- `tau_urg = 0.15m`

解释：

- target 离守区越近，`g_urg` 越接近 1
- 这时团队更应该学“堵门”
- target 还远时，才更需要展开和施压

### 4.3 单机堵截分数

对每架 pursuer `i`，记：

- `v_i = p_i - p_t`
- `d_i = ||v_i||`
- `a_i = <v_i, u_th>`：在 threat axis 上的前后投影
- `l_i = ||v_i - a_i * u_th||`：对 threat axis 的侧向偏差

定义：

```text
block_i =
  sigmoid((a_i - 0.15) / 0.10)
  * sigmoid((||p_g - p_t|| - a_i) / 0.15)
  * exp(-l_i / 0.35)
```

含义：

- 第一项：鼓励站到 target 的前方
- 第二项：鼓励站在 target 与守区之间，而不是跑到守区背后
- 第三项：鼓励贴近 threat axis，而不是偏到侧面太远

### 4.4 团队三项势函数

定义三个团队项，全部压到相对稳定的范围内：

#### A. 堵截项 `phi_block`

```text
phi_block =
  0.7 * max_i(block_i)
  + 0.3 * mean(topk(block_i, k=min(n, 2)))
```

解释：

- 先保证“至少有人真正在堵”
- 再鼓励第二架机形成辅助堵截
- 不用 `sum`，避免人数变多时 reward 人为增大

#### B. 压力项 `phi_pressure`

```text
phi_pressure =
  exp(- mean(topk(d_i, k=min(n, 2))) / r_p)
```

建议：

- `r_p = 0.8m`

解释：

- 只看最近的 1-2 架机
- 这样 `N` 变大时，量级仍然稳定
- 含义是“有没有足够近的 pursuer 持续给 target 压力”

#### C. 展开项 `phi_spread`

```text
phi_spread = 0,                                  if n = 1
phi_spread = 0.5 * (1 - cos(theta_12)),          if n = 2
phi_spread = 1 - ||mean(normalize(v_i))||,       if n >= 3
```

解释：

- `N=1` 时谈不上协同展开
- `N=2` 时最自然的是“双机夹角”
- `N>=3` 时才更适合用 coverage / encircle 的思路

这一步很关键，因为它避免了“一个本来只适合三机包围的几何量，被硬套到所有 `N` 上”。

### 4.5 最终 `Phi_team`

建议定义为：

```text
Phi_team =
  0.50 * (0.4 + 0.6 * g_urg) * phi_block
  + 0.30 * phi_pressure
  + 0.20 * (1 - g_urg) * phi_spread
```

解释：

- `block` 是主项，且在守区临近时权重提高
- `pressure` 始终重要，因为没有压力就很难转化成抓捕
- `spread` 只在 threat 不太紧急时发挥更大作用，避免“临门一脚还在追求漂亮队形”

## 5. 差分边际贡献 D_i

### 5.1 定义

保持 leave-one-out 形式：

```text
D_i = Phi_team(A) - Phi_team(A \ {i})
```

推荐训练时使用裁剪版：

```text
D_i_clip = tanh(D_i / s_D)
```

建议：

- `s_D = 0.15`

### 5.2 特殊情况

- 当 `n = 1` 时，直接设 `D_i = 0`
- 当 `n >= 2` 时，启用 `D_i`

原因：

- 单机情况下不存在协同边际贡献
- 强行计算只会引入噪声

### 5.3 如何使用

优先级建议：

1. 最优先：作为辅助 advantage / auxiliary signal
2. 次优先：作为 reward shaping 项

如果先做简单版，可以先把它作为 reward 项：

```text
r_diff = w_diff * D_i_clip
```

但长期看，更推荐：

- 主 reward 仍围绕任务结果
- `D_i` 用于给 actor 更清晰的局部协同归因

### 5.4 为什么它比“角色专属奖励”更适合

它不要求你人工规定：

- 哪台机必须是 blocker
- 哪台机必须是 flanker
- 哪台机必须一直追最近目标

它只回答一个更普适的问题：

- “如果拿掉这架机，团队的守区防守质量会下降多少？”

这对可变数量 pursuer 尤其重要。

## 6. 指标体系

所有关键指标都建议按 `N` 分开统计，而不是只看全局平均。

### 6.1 结果类

- `capture_before_goal_rate(N)`
- `goal_reached_rate(N)`
- `timeout_rate(N)`
- `median_capture_step | success, N`

这是最核心的一组指标。

### 6.2 防守类

- `urgent_block_rate(N)`
  - 定义：`g_urg > 0.5` 时，`phi_block > 0.6` 的步占比
- `mean_num_blockers(N)`
  - 定义：`block_i > 0.5` 的 pursuer 数量均值
- `threat_axis_ahead_count(N)`
  - 定义：`a_i > 0` 的 pursuer 数量均值

这组指标直接回答：团队有没有真的在守门。

### 6.3 协同类

- `Phi_team_mean(N)`
- `D_i_mean(N)`
- `D_i_min(N)`
- `frac(D_i < 0, N)`

解释：

- `D_i_min` 长期为负，通常表示仍有机体在挤堆或冗余追击
- `frac(D_i < 0)` 下降，说明整体协同分工在改善

### 6.4 队形类

- `phi_spread(N)`
- `max_angle_gap(N)`，只在 `N >= 3` 时看

注意：

- 队形类指标只能作为辅助诊断
- 不能取代防守类与结果类指标

### 6.5 泛化类

- 训练中见过的 `N` 与未见过 `N` 上的 `capture_before_goal_rate` 差值
- `perm_gap(N)`：打乱 agent 顺序后性能差值
- `drop-one-agent gap`
  - 如 `3 -> 2`
  - 如 `4 -> 3`

这组指标决定你到底学到的是：

- 真几何协同
- 还是只是在背编号 / 背固定人数模板

### 6.6 安全类

- `collision_rate(N)`
- `landed_rate(N)`
- `unsafe_speed_rate(N)`

这些指标不应缺席，因为“防守成功”不能靠冒险撞击换取。

## 7. 奖励函数设计：我认为可行的一版

### 7.1 设计原则

- 主目标尽量少，只围绕任务成败
- 协同项要有，但只做辅助，不要压过主目标
- 对 `N` 可变时必须量级稳定
- 安全项更适合作为 cost，而不是无限堆负奖励

### 7.2 推荐形式

定义每架机的 reward：

```text
r_i =
  r_terminal
  + r_goal_progress
  + r_capture_progress
  + w_coop(t) * (0.35 * D_i_clip + 0.15 * Phi_team)
  - lambda_col  * c_collision_i
  - lambda_land * c_landed_env
  - 0.05 * c_speed_i
  - 0.002
```

### 7.3 各项解释

#### A. 终局项 `r_terminal`

```text
r_terminal =
  +10.0 * I(capture_before_goal)
  -10.0 * I(goal_reached)
  - 2.0 * I(timeout)
```

解释：

- 成功抓捕与守区失守必须是最强信号
- 超时要罚，但不需要和失守同级

#### B. 守区进度项 `r_goal_progress`

```text
r_goal_progress =
  0.40 * tanh((d_goal(t+1) - d_goal(t)) / 0.05)
```

解释：

- 如果 target 被逼得离守区更远，得正奖励
- 如果 target 更接近守区，得负奖励
- 这是守区任务里最应该保留的 dense signal

#### C. 抓捕进度项 `r_capture_progress`

```text
r_capture_progress =
  0.20 * tanh((d_team(t) - d_team(t+1)) / 0.05)
```

其中：

```text
d_team = mean(topk(d_i, k=min(n, 2)))
```

解释：

- 只看最接近的 1-2 架机
- 避免人数增加时 reward 被堆高

#### D. 协同项

```text
r_coop =
  w_coop(t) * (0.35 * D_i_clip + 0.15 * Phi_team)
```

解释：

- `D_i_clip` 是主协同信号，负责归因
- `Phi_team` 是次协同信号，负责给团队整体结构一个稳定参考

#### E. 安全项

```text
c_collision_i = 1 if 撞机 / 撞墙 / 撞障碍 else 0
c_landed_env  = 1 if 任意 pursuer 坠地 else 0
c_speed_i     = relu(v_i / v_max - 1)
```

如果采用自适应拉格朗日：

```text
lambda <- [lambda + alpha * (cost_rate - target_rate)]_+
```

建议初值：

- `lambda_col = 2.0`
- `lambda_land = 6.0`

建议目标约束率：

- `collision target_rate = 0.03`
- `landed target_rate = 0.005`

### 7.4 协同项退火

建议：

```text
w_coop(t):
  初期 0.60
  中后期逐步退火到 0.15
  在总训练进度前 50% 左右完成主要退火
```

原因：

- 前期需要协同引导来打破角色坍缩
- 后期应让策略更多对终局任务负责

### 7.5 如果暂时不想上自适应拉格朗日

可以先用固定版：

```text
r_i =
  r_terminal
  + r_goal_progress
  + r_capture_progress
  + w_coop(t) * (0.35 * D_i_clip + 0.15 * Phi_team)
  - 1.5 * c_collision_i
  - 6.0 * c_landed_env
  - 0.05 * c_speed_i
  - 0.002
```

这是一个更容易落地的第一版。

## 8. 与原 `multi_uav_cooperation_design.md` 的关系

本补充文档与原文档的关系可以概括为：

- 保留原文档的核心判断：
  - 协同问题本质上是“表示 + 归因”
  - 差分边际贡献是正确方向
  - 奖励不应继续靠人工堆角色项
- 但在 `goal-defense` 场景下，把：
  - `coverage-only Phi`
  升级为：
  - `block + pressure + N-aware spread` 的 `Phi_team`

也就是说，这不是推翻原方案，而是把它从“协同追捕通用版”进一步收敛成“可变数量 + 守区防守”的任务化版本。

---

## 9. 一句话总结

如果你的目标是：

- 无人机数量可变
- 不只是学会一起追
- 而是真正学会在守区前协同堵截并完成抓捕

那么最合理的主线不是继续手工调 `encircle/intercept` 系数，而是：

```text
任务主目标
+ 守区感知的 Phi_team
+ leave-one-out 的 D_i
+ 按 N 分解的指标体系
+ 退火式协同辅助奖励
```

其中：

- `D_i` 的形式可以继续用
- 但 `Phi_team` 必须换成守区防守版本

这一步，是把“协同追捕”真正推进到“协同守门”的关键。
